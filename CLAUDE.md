@AGENTS.md

## What this is

Arcade Vault: a retro-styled web platform for playing browser arcade games and competing on score leaderboards ("Salón de la Fama"). It is built with **Spec Driven Design** — every feature starts as a spec in `specs/` and is implemented with `/spec-impl` (see **Skills & automation**).

Current state: specs `01`–`12` are implemented (`specs/03-about-page-contacto.md` is the only one still marked `Implementar`). The app has seven real routes, a Supabase-backed catalog and leaderboard, and **five playable games** with real engines: asteroides, tetris, arkanoid, snake, frogger (`references/catalogo-juegos.md` is a hand-kept snapshot and does not list frogger yet). Mobile has a virtual gamepad + fullscreen (specs `10`, `11`). Auth is real Supabase Auth (spec `12`, see **Routes** and **Auth**).

Frogger was built from scratch (no `started-games` reference) from `specs/game-jam/frogger/01-frogger-core.md`, implemented in place instead of being promoted to the root of `specs/`.

Specs are written in Spanish, as are code comments. Keep both when adding to them.

## Commands

- `npm run dev` — dev server (also regenerates `AGENTS.md`, see that file)
- `npm run build` — production build
- `npm run start` — run a production build
- `npm run lint` — ESLint (flat config: `eslint-config-next` core-web-vitals + typescript + `eslint-config-prettier`; `references/**` is ignored)
- `npx prettier --write <path>` — formatting (100 cols, double quotes, trailing commas)

There is no test runner. Features are verified by hand in the browser, usually through the Playwright MCP server; screenshots go in `.playwright-screenshot/`.

| -------------------- | --------------- | --------------------------------------------------------------------------------------------------------------- |

| `/auth/nueva-clave`  | new password    | Reached from the recovery email via `/auth/callback?next=…`; `updatePassword` action.                           |

Pages are Server Components that fetch through `lib/games-repo.ts` and pass data into `"use client"` view components in `components/`.

## Auth

- Spec `12`. Server Actions in `app/auth/actions.ts` (`signUp`, `signIn`, `signOut`, `signInWithOAuth`, `requestPasswordReset`, `updatePassword`; form state `AuthState`); validation and Spanish messages live there. Return URLs use the request `origin` header (no env var).
- `proxy.ts` (root) → `lib/supabase/proxy.ts` `updateSession()`: refreshes the session with `getUser()` on every request and redirects `/auth` (except `callback`, `nueva-clave`) to `/` when logged in. No route requires a session: guest mode stays and `submitScore` is still anonymous.
- `lib/session.ts` — `useUser(): User | null` (`User = { name }`, username in uppercase) from `onAuthStateChange` + `profiles.username`; removes the legacy `av_user` key. There is no `setUser`: logout is the `signOut` action (`Nav` also calls `router.refresh()`).
- `public.profiles` (`id` → `auth.users`, `username` unique case-insensitive, `^[A-Za-z0-9_]{3,12}$`) is filled only by trigger `handle_new_user()` (OAuth usernames autogenerated, suffix `_2`… on collision). RLS: public `select`, no client writes.
- Dashboard config (manual, not in code): "Confirm email" off, min password 8, Password requirements = lowercase + uppercase + digits + symbols (mirrored in `lib/password.ts`, used by `signUp`/`updatePassword` and the `PasswordField` hint; login does not check complexity), sign-up/sign-in rate limit per IP (30 / 5 min), leaked password protection (advisor `auth_leaked_password_protection` still warns: accepted risk, likely Free plan — revisit on upgrade), Site URL + Redirect URLs, Google/GitHub providers, Resend as custom SMTP.

## Data layer

- `lib/supabase/server.ts` / `client.ts` — `@supabase/ssr` clients typed with `lib/supabase/database.types.ts`. Both read `NEXT_PUBLIC_SUPABASE_URL` and `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` with literal `process.env.NAME` access (Next only inlines that form) and throw if missing.
- `lib/games-repo.ts` — the only place that queries Supabase for reads: `getGames()`, `getGame(id)`, `getTopScores(gameId, limit)`, `getGameStats()`. Reuse these instead of adding queries to a page. Score ordering is `score desc, created_at asc` (oldest wins ties).
- `lib/data.ts` — shared types only (`Game`, `GameCategory`, `GameColor`, `GameStats`, `ScoreRow`, `CATS`). The mock catalog is gone; Supabase is the source of truth.
- `lib/format.ts` — `formatPlays()` (`12.4K`), `formatBest()`.
- Server Actions:
  - `submitScore` (`app/juegos/[id]/jugar/actions.ts`) — revalidates the arguments itself (name `^[A-Z0-9_]{1,12}$` — username completo prellenado si hay sesión, score integer 0–9 999 999, game must exist), then revalidates `/salon` and `/juegos/<id>`.
  - `sendContact` (`app/acerca-de/actions.ts`) — `useActionState` shape, honeypot field, Resend send.
- `supabase/migrations/` — timestamped SQL. `games`, `scores` and `profiles` (see **Auth**) with RLS. `games`/`scores`: public `select` on both, public `insert` on `scores` only (constraints repeated in the policy). Schema changes go in a **new** migration file; never edit an applied one. The `supabase` MCP server is configured in `.mcp.json`.
- Env vars live in `.env.local` (git-ignored) and are documented in `.env.example`: Resend (`RESEND_API_KEY`, `CONTACT_TO_EMAIL`, `RESEND_FROM`) and Supabase. Nothing secret gets a `NEXT_PUBLIC_` prefix.

## Game architecture

Each real game is a framework-free TypeScript engine plus a thin React wrapper. Follow this pattern when adding one (`/add-game` writes the spec for it):

1. **Engine** — `lib/games/<id>/`, split as `constants.ts` (sizes, colors, tuning), `entities.ts` (pure state + draw helpers), `engine.ts`, `input.ts`, plus `sprites.ts` / `levels.ts` when needed. `engine.ts` exports `create<Name>Game(canvas, callbacks)` returning a handle (pause, restart, destroy, …). No React, no DOM lookups by id — the canvas arrives as an argument.
2. **Canvas component** — `components/<id>-canvas.tsx`, `"use client"`, implements `GameCanvasProps` from `lib/games/types.ts`: `paused`, `restartKey`, `onScore`, `onLives?`, `onLines?`, `onLevel?`, `onGameOver`, `onTogglePause?`, `onAutoPause?`, `blockStyle?`, `muted?`, `volume?`, `jumpTo?`, `pad?` (`VirtualPad`, stable per match). Keep the callbacks in a ref so prop changes never recreate the engine, mirror `paused` into a ref, and create/destroy the engine in a Strict-Mode-safe `useEffect`.
3. **Registry** — add a `GameEntry` to `GAME_REGISTRY` in `lib/games/registry.ts`: `Canvas`, `controls` (for the controls hint), `engineLevel`, `hasLives`, and optionally `hasLines`, `blockStyles`, `aspect` (default `4 / 3`), `hasSound`, `levelJump`, `touch` (`dpad: PadDir[]`, `diagonals?`, `buttons?` — without it there is no mobile pad). `GamePlayer` drives the HUD entirely from this entry; an id with **no** entry keeps the simulated placeholder.
4. **Catalog + assets** — a row in the `games` table whose `id` equals the route segment (one migration per game, e.g. `supabase/migrations/20261015120000_game_frogger.sql`), a `.cover-<id>` class (or a reused one) in `app/globals.css`, and binaries under `public/games/<id>/`.
5. **Touch** — `lib/games/touch.ts` (`createVirtualPad`: pub/sub channel, no React/DOM) is written by `components/touch-pad.tsx` (neon D-pad with dead zone/diagonals + A/B buttons) and read by each engine's `input.ts` via `subscribe`. `components/game-player.tsx` creates the pad and handles fullscreen (with `webkit*` fallback). Specs: `specs/10-controles-tactiles-moviles.md`, `specs/11-gamepad-movil-neon.md`.

Only draw on canvas what the React HUD cannot show.

Not part of the Next.js build, and excluded from ESLint, Prettier and the format hook. It is the visual/UX source of truth — port from it rather than designing from scratch.

- `templates/` — the original standalone React+Babel CDN prototype (`Arcade Vault.html` opens directly in a browser): `data.jsx`, `app.jsx` (hash router + `localStorage` session, a prototype substitute for routing/auth, not a pattern to copy), `nav.jsx`, `biblioteca.jsx`, `detalle.jsx`, `reproductor.jsx`, `salon.jsx`, `auth.jsx`, and `styles.css` — the full retro/neon design system (CSS custom properties, glow, scanline/CRT textures, pixel font) that `app/globals.css` is derived from.
- `templates/home-about/` — `home.jsx` and `about.jsx`, the sources of `/` and `/acerca-de`.
- `started-games/` — the original playable JS games ported into `lib/games/`: `02-asteroids`, `03-tetris`, `04-arkanoid`. Their **code is the source of truth over their READMEs**.
- `source-assets/` — raw art, e.g. `snake-assets/` (fruit spritesheet).
- `gamepad-assets/` — `gamepad.html` (standalone neon "MK-II" pad), `gamepad-neon.png`, README; source of `touch-pad.tsx` (spec `11`).
- `catalogo-juegos.md` — hand-maintained snapshot of the `games` table; `game-suggestions-todo.md` — append-only ledger of every game the `game-planner` and `game-jam` agents have evaluated (see **Skills & automation**).

## Skills & automation

Workflow skills live in `.claude/skills/` (mirrored in `.agents/skills/` so other agents can read them); they come from `Klerith/fernando-skills` (`skills-lock.json`, `npx skills@latest add Klerith/fernando-skills`).

- `/spec <description>` — interviews first, then writes `specs/NN-slug.md` in state `Borrador`. Writes no code.
- `/spec-impl NN-slug` — refuses unless the state means **Approved** (`Aprobado`/`Approved`); creates and switches to branch `spec-NN-slug`, then implements the plan step by step pausing for diff review. It never commits on its own. Branch creation is governed by `AutoCreateBranch` in `specs/.spec-config.yml` (currently `true`).
- `/spec-impl-game NN-juego-id` — wraps `/spec-impl` for game specs: runs it as-is (it can't be invoked via Skill, so the skill reads and follows `spec-impl/SKILL.md`), then runs agent `skin-designer` and, only once it finishes, agent `mobile-porter` — strictly sequential, never parallel. Never commits.
- Agent `game-planner` (`.claude/agents/game-planner.md`, mirrored in `.agents/agents/`) — decides **which** game to add, before `/add-game`: scores candidates on technical fit, scoring fit and catalog diversity, picks one, and records every candidate it evaluates in `references/game-suggestions-todo.md` so it never repeats a suggestion. Writes no code and no specs; hands off a brief for `/add-game`.
- Agent `game-jam` (`.claude/agents/game-jam.md`, mirrored in `.agents/agents/`) — turns a **theme** into a mini design jam: picks the game, its `id` and its catalog row, then writes `specs/game-jam/<id>/` with `00-brief.md` (comparison table + recommendation), `00-preguntas.md` (open questions, each with the default already applied) and **three complete, self-sufficient specs of the same game** — `A-juego-<id>.md` (minimal faithful), `B-juego-<id>.md` (one twist), `C-juego-<id>.md` (ambitious) — all in state `Borrador`, shaped by `.claude/skills/add-game/game-spec-template.md` and modelled on specs `07`–`09`. Writes no code, applies no migrations (read-only `select` only), and touches no spec in the root of `specs/`. To build one: copy it to `specs/NN-juego-<id>.md`, set the state to `Aprobado` and run `/spec-impl` — `/spec-impl` lists `specs/` without recursing, so the promotion is manual and deliberate. The chain: `game-planner` picks **which** game · `game-jam` proposes **three designs** from a theme · `/add-game` writes **one** spec after interviewing.
- Existing game-jams in `specs/game-jam/`: `invasores/`, `gloton/`, `columnas/` (all `Borrador`, none promoted yet) and `frogger/` (implemented).
- Agent `skin-designer` (`.claude/agents/skin-designer.md`, mirrored in `.agents/agents/`) — audits real-engine games missing the block/sprite skins `bisel`, `plano`, `neón`, `contorno` (reference: tetris) and implements them across engine, canvas and registry (`blockStyles`). Run by `/spec-impl-game`, or on its own after adding a game.
- Agent `mobile-porter` (`.claude/agents/mobile-porter.md`, mirrored in `.agents/agents/`) — audits every route on emulated touch viewports (390×844, 844×390, tablet) with Playwright, using `specs/10-controles-tactiles-moviles.md` (and the pad of `specs/11-gamepad-movil-neon.md`) as the reference, then fixes mobile layout/gestures/safe areas in `app/globals.css` and components. Desktop must not change; no commits, no DB, no PWA unless asked.
- Agent `security-auditor` (`.claude/agents/security-auditor.md`, mirrored in `.agents/agents/`) — **read-only** audit of Supabase (advisors, RLS, policies, grants, `security definer` functions, migrations drift) and the app (auth actions, callback `next`, proxy, headers, secrets, `npm audit`) against specs `12`/`13` and `references/security/security-checklist.md`. Writes a dated report to `references/security/audits/YYYY-MM-DD.md` with a diff vs the previous one (new / resolved / persistent). Never edits code, applies migrations or commits; SQL fixes appear only as drafts in the report.
- `/add-game <started-games folder | description>` — project-specific skill that wraps `/spec` for new games: analyzes the reference, asks about catalog row / HUD / controls / scoring, and saves `specs/NN-juego-<id>.md`. Canonical models: `specs/05-juego-asteroides.md` and `specs/06-leaderboard-y-catalogo-supabase.md`.
- Usa siempre `/frontend-design` para diseñar la interfaz de usuario.

A `PostToolUse` hook in `.claude/settings.json` runs `.claude/hooks/format.mjs` after every Write/Edit: it strips trailing whitespace, then `prettier --write`, then `eslint --fix` for code files, and **fails the tool call** on a lint error. Don't hand-format files, and fix reported lint errors rather than working around the hook.

## Stack notes

- Next.js 16.3.6 App Router, React 19.2, TypeScript, Tailwind CSS v4 (CSS-first config via `@theme inline` in `app/globals.css` — a ~3000-line design system, no `tailwind.config.*` file).
- Security headers (spec `13`) are set in `next.config.ts` `headers()` for `/(.*)`: `X-Content-Type-Options`, `X-Frame-Options: DENY`, `Referrer-Policy`, `Strict-Transport-Security` (no preload), `Permissions-Policy` (`fullscreen=(self)` is needed by the gamepad). No CSP yet.
- `@supabase/ssr` + `@supabase/supabase-js`, `resend`.
- `tsconfig.json` uses `@/*` path aliases rooted at the repo root.
- Route prop types (e.g. `LayoutProps<"/">` in `app/layout.tsx`) come from Next's generated `.next/types` — check the App Router API reference under `node_modules/next/dist/docs/01-app/03-api-reference/` when working with route/layout/page prop typing, since this is a newer convention.
